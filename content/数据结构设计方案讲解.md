### 第一页
今天我们汇报的主题是“个性化旅游系统设计方案与开发汇报”。在本次项目中，我们不仅完成了从底层图算法到上层应用的全栈构建，还进行了一些AI技术的探索实践。


### 第二页
我们项目的核心目标是构建一个前后端分离的个性化旅游系统，旨在完全打通“查询-规划-推荐-记录-展示”的全流程闭环。在这个闭环中，系统支持从前期的地点搜索，到路线生成，再到最后的游记内容沉淀。 为了达到课程的硬性技术要求，我们给自己设立了严格的技术红线：首先，核心模块绝对禁止调用诸如 networkx 这样的高级算法库，必须纯手写实现；其次，系统的查询主路径绝不能退化为 O(n) 的全表扫描。

### 第三页
在系统架构层面（第三页），我们采用了前后端分离的设计。开发环境基于 Python 3.10+ 和 Node.js 18+ 构建。 前端部分，我们选用了 Vue 3 框架，主要负责用户的交互输入、地图展示以及路线结果的直观可视化。 后端部分，我们基于 FastAPI 框架搭建，并将其严格划分为四个核心目录层

### 第四页
除了**利用“龙虾”和大模型辅助生成 FastAPI 路由骨架与前端交互雏形，我们在个性化旅游推荐模块，计划引入多智能体理念或多维度标签机制，通过对旅游场所的热度、用户评价以及兴趣标签进行联合打分，来实现精准推荐。 此外，在旅游日记管理模块，我们设计了 AIGC 扩展功能，支持调用第三方 API 自动生成短视频链接，作为游记的多媒体增强手段。

### 第五页
 接下来是第五页，核心算法设计的第一部分。我们的系统需要支持 200 多个景区以及海量的设施数据。为了满足“不退化为 O(n) 扫描”的红线，系统启动后会自动构建 Trie（字典树）索引，这样就能高效支持前缀和拆词检索。 在排序上，项目要求距离排序必须以“图路径距离”为准，绝不能用直线距离糊弄过去。为此，我们通过纯手写的堆（Max Heap 或固定大小的 Min Heap）来实现 Top-K 检索，将时间复杂度严格控制在 O(N log K)，完美避免了全量排序带来的性能损耗。

### 第六页
路线规划的核心逻辑。针对基础的多策略规划，我们使用手写的 Dijkstra 算法来计算最短距离；如果要计算最短时间，我们会将边权动态设置为“距离/速度”，并且速度可以根据拥挤度进行调整。 在室内导航场景中，我们为节点引入了楼层（floor）属性，将电梯或楼梯视为跨楼层的特殊边。而面对小于 10 个节点的多点路径规划（TSP）难题，我们采用了状态压缩 DP 或回溯算法来求得最优解。

### 旅游日记 第七页
关于旅游日记的内容沉淀。为了实现游记文本的高效检索，我们手写了倒排索引，将搜索关键词精准映射到对应的日记 ID 列表上。同时，为了实现数据的无损压缩，我们还全程手写了 Huffman 编码与解码的底层流程。
